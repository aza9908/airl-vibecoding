# Шаг 3 — Безопасность: можно ли это показывать людям

## 📚 Покажи это человеку перед первым вопросом

```
🔒 Шаг 3 из 3 — Безопасность

Продукт работает. Теперь проверим, безопасно ли показывать его живым людям.

Скажу сразу, чтобы снять лишнюю тревогу: в небольших продуктах утечки почти
никогда не происходят из-за хитрых атак. Причина обычно одна из трёх —
ключ доступа случайно попал в общий репозиторий, права проверяются только тем,
что кнопка спрятана, или у платного сервиса не стоит потолок расходов.

Задам 5 вопросов, потом пройду проект по списку. Часть находок починю сам,
часть придётся сделать вам руками — напишу пошагово, куда зайти и что нажать.

В конце отвечу прямо: можно выкладывать или нет.
```

## Жёсткие правила

- **Значения ключей и паролей не печатаются никогда** — ни в переписке, ни в отчёте,
  ни в примерах. Только имя переменной и файл, где она лежит.
- Ключ, попавший в историю репозитория, считается **скомпрометированным**. Удалить
  строку недостаточно, нужна замена ключа в кабинете сервиса. Объясни это прямо.
- В боевой среде ничего не меняется без явного «да».

## Режим существующего проекта

Проверка одинаковая для нового и старого проекта — разница только в том, что в старом
находок обычно больше. Не пугай этим человека и не читай нотаций: покажи список
и раздели на «срочно» и «можно позже».

## Как задавать вопросы

Один вопрос за сообщение, 3–4 варианта, рекомендация первой строкой. Ответ «не знаю» —
бери рекомендацию и скажи об этом.

## Пять вопросов

**1. Какие данные хранит продукт?**
Никаких · обычные (имена, телефоны, заявки) · документы · платёжные данные.
Чем чувствительнее, тем строже проверка — скажи это вслух.

**2. Кто может зайти в продукт?**
Только сотрудники · клиенты после регистрации · любой человек из интернета.

**3. Может ли один пользователь увидеть данные другого?**
Не должен ни при каких условиях · есть общие данные для всех · администратор видит всё.
Самая частая дыра, поэтому вопрос обязательный.

**4. Есть ли платные сервисы с оплатой по факту использования?**
Нет · модель ИИ · рассылки или SMS · несколько сразу. Здесь риск не утечки,
а неожиданного счёта.

**5. Продукт уже выложен в интернет?**
Ещё нет · по временной ссылке · на боевом домене.

## Проверка: пять групп

### 1. Ключи и пароли

`.env` записан в `.gitignore` · есть `.env.example` с именами, но без значений ·
в коде нет ключей и токенов · ключей нет в истории репозитория · публичный префикс
(`NEXT_PUBLIC_`, `VITE_`) стоит только у действительно публичных значений, иначе секрет
уезжает в браузер каждого посетителя · ключи не попадают в собранный файл для браузера.

### 2. Доступ к данным

Права проверяются **на сервере**, а не тем, что кнопка спрятана · пользователь не может
открыть чужую запись, подставив другой номер в адресе · правила доступа в базе настроены,
а не оставлены открытыми по умолчанию · действия администратора отделены от обычных.

Проверяй не чтением кода, а попыткой: подставь чужой идентификатор и посмотри, что вернётся.

### 3. Вводимые данные

Проверяются на сервере, а не только в браузере · запросы к базе не собираются склейкой
строк · загрузка файлов ограничена по типу и размеру · текст от пользователя не выводится
как разметка · сообщения об ошибках не показывают внутренности: пути, версии, стек вызовов.

### 4. Деньги

У каждого платного сервиса стоит **жёсткий потолок расходов**, а не уведомление на почту —
уведомление приходит уже после счёта · описано, что происходит при исчерпании лимита ·
оплата подтверждается на сервере, а не по ответу браузера · повторное нажатие не создаёт
вторую операцию.

### 5. Боевая среда

Ключи для разработки и боевой версии разные · боевые данные отделены от тестовых ·
отладочный режим выключен · в логи не пишутся пароли, токены и персональные данные ·
есть способ вернуться к предыдущей версии.

## Результат — покажи в переписке

Запиши `SECURITY.md`, но человека читать его не отправляй. Покажи здесь:

```
## 🔒 Проверка закончена

**Можно показывать людям: ДА** — с одной оговоркой ниже.

| Срочность | Что нашли | Кто чинит |
|-----------|-----------|-----------|
| 🔴 Срочно | ключ доступа в истории репозитория | вы: заменить ключ |
| 🟡 Важно | права проверяются только в интерфейсе | я, уже исправил |
| ⚪️ Можно позже | нет потолка расходов на ИИ | вы, 3 минуты |

**Что я исправил**: [список одной строкой каждый пункт]

**Что нужно сделать вам**

### 1. Поставить потолок расходов
Зачем: сейчас при всплеске нагрузки счёт может вырасти без предупреждения.

1. Зайдите на [адрес]
2. Откройте раздел [название]
3. Задайте месячный лимит [сумма]
4. Проверка: должно появиться [что именно]
```

Три уровня: 🔴 **срочно** — выкладывать нельзя · 🟡 **важно** — выложить можно, исправить
на этой неделе · ⚪️ **можно позже** — не мешает работе.

Ничего не нашёл — так и скажи. Не выдумывай находки, чтобы отчёт выглядел солиднее.

## Что чинишь сам

Сначала покажи список правок, получи согласие, потом правь. Сам можешь: добавить `.env`
в `.gitignore`, вынести ключ в переменную, добавить проверку прав на сервере, добавить
проверку вводимых данных, создать `.env.example`.

Только человек, руками в кабинете: замена утёкшего ключа, потолки расходов, двухфакторный
вход, резервные копии, настройки домена.

## В конце

Скажи прямым текстом одно из двух:

- «Продукт можно показывать людям. В ближайшую неделю стоит сделать вот это: …»
- «Пока выкладывать нельзя. Мешает вот это: … Как исправите — запустите `/airl-security`
  ещё раз, проверю повторно».

Затем, если запущен из `/airl-start`, верни управление ему для предложения публикации.
Если запущен отдельно и продукт готов — предложи опубликовать через Netlify или Firebase.

## Чего не делать

- Не печатать значения ключей и паролей.
- Не считать удаление строки решением для утёкшего ключа.
- Не менять ничего в боевой среде без явного согласия.
- Не пугать сложными словами: объяснять простым языком, что может случиться и чем грозит.
- Не отправлять человека читать файл вместо показа в переписке.
